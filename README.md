# payment-architecture

결제 아키텍처를 단계적으로 구현하기 위한 학습 프로젝트입니다.

## 실행

Toss 시크릿 키가 없으면 기동되지 않습니다. 설정 누락이 결제 시점에 드러나지 않도록 핸들러 생성 시점에 확인합니다.

```
TOSS_SECRET_KEY=<키> ./gradlew bootRun
```

## Step 1

- Spring Boot + Kotlin
- MyBatis
- H2 인메모리 데이터베이스

이 단계에서는 애플리케이션 기동과 데이터 접근 환경만 구성합니다. 도메인 모델, 테이블, SQL Mapper, 결제 기능은 다음 단계에서 추가합니다.

## Step 2

Toss 빌링 결제에 멱등성을 적용합니다.

- 동일 주문 중복 결제 방지: `prepare()`에서 주문 row를 `SELECT ... FOR UPDATE`로 잠그고, 이미 PENDING 거래가 있으면 새 결제를 만들지 않고 그 상태를 그대로 반환합니다.
- PENDING 만료 및 재처리: Toss 승인 응답이 타임아웃 등으로 불확실(`Unknown`)하면 즉시 실패시키지 않고 PENDING으로 유지합니다. 만료된 PENDING 거래는 스케줄러가 Toss 결제 조회 API로 실제 상태를 재확인해 완료/실패를 확정하고, 최대 재처리 기간이 지나도 확정되지 않으면 실패로 처리합니다(실패 확정 직전 취소(망취소) API 호출은 TODO로 남겨둠).

## Step 3

장바구니에서 결제까지 이어지는 화면(Thymeleaf)을 붙이고, 결제 결과를 사용자에게 되돌려주는 경로를 정비합니다. 상품 목록과 결제 대상 회사는 학습 단계 범위상 하드코딩하고, 장바구니는 서버에 두지 않고 브라우저 `localStorage`로만 관리합니다.

- 화면: 상품 목록 → 장바구니 → 결제 → 결과. 결제 제출은 별도 엔드포인트를 만들지 않고 기존 `POST /api/payments`를 그대로 호출합니다. Toss 빌링키 발급 API(`POST /api/companies/{companySeq}/billing-keys`)도 함께 추가했습니다.
- 결과 처리: 응답의 결제 상태에 따라 나눕니다. 성공이면 장바구니를 비우고 결과 페이지로, 실패면 장바구니를 유지한 채 체크아웃에 머물며 사유를 보여주고, 아직 확정되지 않았으면(`PENDING`) 결과 페이지에서 지수 백오프로 폴링합니다. 응답을 받지 못한 경우(타임아웃·네트워크 오류)도 결과 페이지에서 실제 상태를 확인합니다.
- 중복 결제 방어: `orderKey`는 장바구니가 바뀔 때만 새로 발급해 재시도가 같은 주문으로 이어지게 하고, `paymentKey`는 시도마다 새로 만듭니다. 서버는 주문 row를 잠근 뒤 진행 중인 거래와 이미 결제된 주문을 확인해 중복 승인을 거부합니다.
- 주문 상태 정리: 한 주문에 여러 결제 시도가 붙을 수 있으므로, 결제 실패는 주문의 종료 상태가 아니라 시도의 결과로만 기록합니다. 주문은 결제될 때까지 `PENDING_PAYMENT`로 두고 시도별 결과는 `payment_transaction`에 남깁니다.

무신사·쿠팡·네이버의 실제 결제 흐름을 네트워크 캡처로 비교해 방향을 정했습니다. 세 곳 모두 승인은 서버가 수행하며, 차이는 결제 시점에 별도의 인증 단계를 두느냐입니다. 빌링키 방식인 이 프로젝트는 그 인증이 빌링키 발급 시점에 끝나 있어, 요청이 서버에 도달하는 순간 승인이 일어납니다. 그래서 결과를 사용자에게 되돌려줄 경로(결과 페이지와 폴링)가 별도로 필요합니다.

## Step 4

Step 3까지 만든 흐름에 남아 있던 구멍을 메웁니다. 아키텍처를 바꾸는 단계는 아닙니다.

- 결제 금액 검증: 요청 항목에서 상품명과 단가를 없애고 `productId`만 받습니다. 이름과 가격은 서버가 조회한 상품에서 가져오고, 재계산한 합계가 클라이언트가 보낸 `totalPrice`와 다르면 승인 전에 거부합니다. 그 전까지는 클라이언트가 보낸 금액을 그대로 승인했습니다. 검증은 DTO가 아니라 `prepare()`에서 합니다. DTO는 입력 형태만 보고, DB 조회가 필요한 검증은 서비스가 맡습니다. 하드코딩되어 있던 상품 목록도 이때 `product` 테이블로 옮겼습니다.
- 같은 주문의 항목 고정: 합계가 같아도 상품 구성은 다를 수 있습니다(예: 6500×2와 5000+3800+4200). 기존 주문으로 재시도할 때 저장된 항목은 갱신하지 않으므로, 구성이 다르면 회사·금액 검사와 같은 정책으로 거부합니다.
- 예외를 HTTP 상태에 맞게 매핑: 이미 결제된 주문 거부가 500으로 나가 클라이언트가 "다시 시도해 주세요"를 띄우던 문제를 고칩니다. 재시도해도 계속 막히므로 잘못된 안내였습니다. `@RestControllerAdvice`에서 `OrderAlreadyPaidException`을 409로, `IllegalArgumentException`을 400으로 매핑하고 본문은 ProblemDetail(RFC 9457)로 통일합니다. 400은 내부 예외 메시지를 노출하지 않고 고정 안내를 주며 사유는 로그에 남깁니다. 서버 불변식이 깨진 경우(`IllegalStateException` 등)는 핸들러를 달지 않고 서블릿의 `/error`로 흘려보냅니다. 클라이언트는 409에서만 장바구니를 비우고 그 외 오류는 유지해 그 자리에서 재시도할 수 있게 합니다.
- 실패 사유 보존: `payment_transaction`에 `fail_code`, `fail_message`를 추가해 승인 실패와 재처리 실패 확정 시 함께 기록하고 폴링 응답으로 내보냅니다. 그 전에는 사유가 승인 응답에만 있어, 재처리가 PENDING을 FAILED로 확정하면 결과 페이지에 상태만 남았습니다.
- 외부 호출과 트랜잭션 분리: 빌링키 발급에서 `@Transactional`을 제거합니다. 분기마다 쓰기가 하나뿐이라 묶을 것이 없고, 트랜잭션의 유일한 효과가 Toss 응답을 기다리는 동안 DB 커넥션을 붙잡는 것이었습니다.
- Toss 핸들러 통합: 발급과 승인 핸들러가 나뉘어 있어 같은 시크릿 키 검사를 중복해야 했습니다. 하나로 합치고 검사를 생성 시점(`init`)으로 옮깁니다. 설정 누락이 결제 시점이 아니라 기동 시점에 드러나고, 승인 직전에 터져 PENDING 거래가 남는 경로도 없어집니다.

비동기 승인(네이버식)은 하지 않기로 했습니다. 무신사와 쿠팡도 동기 승인에 폴링 폴백을 두고 운영하는 것을 캡처로 확인했고, 비동기 전환의 이유는 정확성이 아니라 부하 특성이므로 지금 규모에서 갈 이유가 없습니다. 전환 조건과 방법은 코드에 TODO로 남겨두었습니다. 인증이 붙은 뒤 주문·결제 키에 회사 식별자를 섞어 회사별 네임스페이스를 만드는 방안도 함께 기록해 두었습니다.

망취소(승인 요청은 보냈으나 응답을 잃은 경우 되돌리기)는 다음 단계로 남겨두었습니다.

## Step 5

배송예정일 개념을 들여옵니다. 외부 업체에 주문을 넘기는 마감이 있으므로, 마감 전 주문은 내일 도착, 이후 주문은 모레 도착으로 **보장**합니다. 예정이 아니라 보장이므로 지킬 수 없는 날짜는 애초에 팔지 않습니다.

- 배송 보장일: `order`에 `delivery_date`를 두고, 마감 시각(`payment.delivery.cutoff-hour`, 기본 22시) 전이면 D+1, 이후면 D+2로 계산합니다. 계산 규칙은 주문의 성질이므로 `OrderService`가 갖습니다.
- 결제 시 검증: 클라이언트는 화면에서 본 보장일을 요청에 실어 보내고, 서버가 재계산한 값과 다르면 승인 전에 거부합니다(409). 화면을 띄워둔 채 마감을 넘긴 경우가 여기 걸립니다. 금액 검증과 같은 방식이지만 대조 대상이 다릅니다. 금액은 변하지 않는 값이라 저장값과 맞추고, 보장일은 시간이 지나면 변하므로 항상 지금 계산한 값과 맞춥니다.
- 재시도 시 갱신: 결제되기 전까지 보장일은 계약이 아닙니다. 마감을 넘겨 낡은 값이 저장된 주문을 같은 `orderKey`로 재시도하면, 지금 약속 가능한 값으로 갱신하고 진행합니다. 저장값과 대조했다면 그 주문은 영영 결제할 수 없게 됩니다.
- 체크아웃 미리보기 API: `POST /api/checkout/preview`가 상품명·단가·합계·보장일을 서버가 계산해 내려줍니다. 화면 표시와 결제 요청이 모두 이 응답을 쓰므로, 클라이언트가 계산 규칙을 복제할 필요가 없고 브라우저 시계와 어긋날 일도 없습니다. 결제 요청의 항목까지 미리보기에서 가져와, 값의 출처를 하나로 맞췄습니다.
- 오류 코드: 409가 "이미 결제됨"과 "보장일 변경" 두 종류가 되었습니다. 클라이언트가 구분해야 처분이 갈리므로(전자는 장바구니를 비우고, 후자는 유지한 채 미리보기를 다시 받음) ProblemDetail의 `type`에 식별자를 실어 보냅니다.

보장을 지키지 못하게 되었을 때의 처분은 아직 정하지 않았습니다. 결제가 늦게 확정되어(재처리가 PENDING을 뒤늦게 성공으로 확정) 이미 마감이 지난 경우가 그렇습니다. 취소해서 없던 일로 하는 방안과, 다음 회차로 미루고 보상하는 방안(쿠팡식)을 코드에 TODO로 적어두었습니다. 후자를 택하면 약속한 날짜와 실제 태울 날짜를 둘 다 저장해야 합니다.

마감을 지키기 위한 스케줄러 개편도 다음 단계입니다. 지금 재처리는 경과 시간 기준(생성 후 5분에 첫 조회, 30분에 실패 확정)인데 마감은 절대 시각 기준이라, 마감 직전에 만들어진 거래는 두 기준 모두 마감을 넘깁니다. 망취소와 함께 다루어야 하므로 묶어서 남겨두었습니다.

## Step 6

승인 응답을 잃은 거래를 되돌리는 망취소를 붙이고, 마감 시각에 다음날 배송분을 외부 업체로 넘깁니다. Step 5에서 남겨둔 "마감을 지키기 위한 스케줄러 개편"이 이 단계입니다.

- 확정 기한과 망취소: 거래는 생성 후 5분 안에 성공이나 실패로 끝냅니다. 기한을 넘긴 PENDING 거래는 조회해서 승인이 성공했으면 취소하고, 조회로도 확정하지 못하면 승인이 도달한 적 없는 것으로 보고 실패로 종료합니다. 5분은 임의 값이 아니라 승인 호출의 HTTP 타임아웃(연결 10초 + 읽기 60초)에서 유도한 값입니다. 취소를 쏘는 시점에 아직 날아다니는 승인 요청이 없어야 하기 때문입니다. 업계 표준보다 늦게 쏘는 이유는 Toss 취소 API가 승인 응답에만 있는 `tid`를 요구해 선제적으로 막을 수단이 없어서입니다. 조회로 알아내야 하므로 기다렸다 판단할 수밖에 없습니다.
- 승인 중인 거래를 집지 않기: 재처리 대상을 생성 후 90초가 지난 거래로 제한합니다. 그 전에는 승인이 아직 진행 중일 수 있고, 그때 재처리가 상태를 바꾸면 승인 쪽 조건부 갱신이 0행이 되어 클라이언트가 500을 받았습니다.
- 시간 기준을 하나로: `expired_at`을 `next_check_at`으로 바꿨다가 컬럼 자체를 없애고 `created_at`으로 대체했습니다. 다음 확인 시각은 생성 시각에서 계산할 수 있는 파생 값이라, 저장해 두면 같은 사실을 두 곳에서 말하게 되고 갱신을 빠뜨리면 어긋납니다. 첫 확인 대기(90초)와 확정 기한(300초) 규칙은 `PaymentTransaction`으로 옮겨 시간 판단을 한 곳에 모았습니다.
- 상태를 늘리지 않기: "망취소 대기" 상태는 만들지 않았습니다. `created_at`이 이미 그 정보를 갖고("PENDING인데 5분 지남"), 취소 실패도 PENDING으로 두면 다음 회차가 자동으로 재시도합니다.
- 마감 전달: 마감 직후(`payment.delivery.handoff-cron`, 기본 22시 5분) 다음날 배송분을 외부 업체로 넘깁니다. 붙일 외부 시스템이 아직 없어 상태 전이가 전달을 대신합니다. 대상을 `PAID`로만 잡으므로 이미 넘긴 주문은 다시 걸리지 않고, 결제가 확정되지 않은 주문은 애초에 대상이 아닙니다. 그래서 재처리 스케줄러와 실행 순서를 맞출 필요가 없습니다.

재처리 회차가 밀리는 문제는 대책을 넣지 않기로 했습니다. 회차를 미는 70초짜리 조회는 응답이 아니라 타임아웃이고 결과가 불확실이라, 밀림이 일어나는 구간은 Toss 장애 하나뿐이며 그때는 병렬로 돌려도 얻는 것이 없습니다. 실제 피해는 확인하지 못한 채 실패로 종료하는 것이고, 그것은 다음 단계의 일일 대사가 받습니다. 판단 근거는 설계 노트에 남겼습니다.
